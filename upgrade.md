## 1. Современный дизайн WPF

**Подход:** собственный стиль на XAML, без сторонних UI-библиотек. Material-подобная палитра, скруглённые углы, единая система ресурсов, поддержка тёмной/светлой темы. Полный контроль над внешним видом, ноль новых зависимостей.

### 1.1. Система ресурсов (новый файл `Themes/Colors.xaml`, `Themes/Fonts.xaml`)

Централизованная палитра через `ResourceDictionary`, чтобы не дублировать цвета по всем окнам:

```xml
<!-- Цвета статусов (используются и в TreeView, и в отчётах) -->
<SolidColorBrush x:Key="StatusOkBrush"        Color="#2E7D32"/>
<SolidColorBrush x:Key="StatusWarningBrush"   Color="#F9A825"/>
<SolidColorBrush x:Key="StatusFailBrush"      Color="#C62828"/>
<SolidColorBrush x:Key="StatusErrorBrush"     Color="#6D4C41"/>

<!-- Акцент, фон, поверхности -->
<SolidColorBrush x:Key="WindowBackground"     Color="#F5F5F7"/>
<SolidColorBrush x:Key="SurfaceBrush"         Color="#FFFFFF"/>
<SolidColorBrush x:Key="AccentBrush"          Color="#3B82F6"/>
<SolidColorBrush x:Key="TextPrimaryBrush"     Color="#1F2937"/>
<SolidColorBrush x:Key="TextSecondaryBrush"   Color="#6B7280"/>
```

Подключается в `App.xaml` через `MergedDictionaries` → сразу доступно во всех окнах. Сейчас цвета захардкожены прямо в `MainWindow.xaml` (`#FF2E7D32`, `#FFC62828` и т.д.) — это и копится, и мешает темам.

### 1.2. Переиспользуемые `ControlStyle` (новый файл `Themes/Controls.xaml`)

Сейчас у каждой кнопки дублируются `Width/Height/Margin/FontSize`. Будут стили:

- `PrimaryButtonStyle` — основная кнопка (синий акцент, скруглённые углы, hover-эффект через `ControlTemplate`).
- `SecondaryButtonStyle` — второстепенная (плоская, серая).
- `DangerButtonStyle` — удаление (красный акцент).
- `CardStyle` — карточка-панель с тенью и скруглением для группировки контента.

### 1.3. Реструктуризация `MainWindow.xaml`

Текущий лейаут (два `StackPanel` с кнопками в ряд) на узких экранах переполняется по ширине. Будет:

- **Шапка**: заголовок «Backup Monitor» + индикатор статуса службы (цветной кружок + текст) справа.
- **Toolbar**: кнопки в `WrapPanel`, чтобы они переносились на следующую строку при нехватке места.
- **Карточка статуса службы**: отдельная панель с кнопками «Запустить/Остановить/Обновить» и живым индикатором статуса.
- **Список сервисов**: `TreeView` с улучшенными `HierarchicalDataTemplate` — карточки с резкими разделителями, крупные индикаторы статуса, моноширинный шрифт для путей.
- **Статус-бар внизу**: тонкая полоса с сообщением и временем последней проверки.

### 1.4. Тёмная/светлая тема

Через `App.xaml` и переключатель в шапке (иконка солнце/луна). Все цвета берутся из ресурсов → тема переключается заменой `ResourceDictionary` во время выполнения. Настройка сохраняется в `appconfig.json`.

### 1.5. Окна диалогов (`ServiceWindow`, `BulkServiceWindow`, `TelegramSettingsWindow` и др.)

### 1.6. Иконки

## 2. Интерактивный Telegram-бот (отчёты по запросу)

**Подход:** long polling через `getUpdates` — служба сама опрашивает Telegram, не требует белого IP/вебхука. **Доступ** — белый список `AllowedChatIds` в конфиге; команды от посторонних игнорируются.

Сейчас бот умеет **только отправлять** отчёты по расписанию (`sendMessage`). Чтобы принимать команды, нужно получать входящие сообщения (`getUpdates`) и обрабатывать их.

### 2.1. Новые поля в конфиге (`TelegramConfig`)

```csharp
public class TelegramConfig
{
    // ... существующие поля ...

    // Разрешённые chat_id для приёма команд (безопасность)
    public List<string> AllowedChatIds { get; set; } = new();

    // Включить приём команд (отдельный флаг — можно оставить только рассылку)
    public bool EnableCommands { get; set; } = false;

    // Offset для getUpdates (хранится в памяти, не в конфиге)
    // — управляется ботом, в файл не пишется
}
```

### 2.2. Система команд (новый сервис `TelegramCommandBot`)

Новый сервис в `BackupMonitor.Core/Services/TelegramCommandBot.cs`, отдельно от `TelegramReportSender` (ответственность: «отправлять отчёты» и «принимать команды» — разные).

**Жизненный цикл:**
- Запускается в `BackupMonitorWorker` как фоновый цикл (параллельно основному таймеру рассылки).
- Каждые ~2 сек вызывает `getUpdates` с `offset` (подтверждение обработки → Telegram удаляет сообщение из очереди).
- При получении сообщения парсит команду, проверяет `AllowedChatIds`, формирует отчёт и шлёт ответ через `TelegramReportSender`.

**Список команд:**

| Команда | Описание |
|---|---|
| `/start`, `/help` | Список доступных команд |
| `/report` или `/status` | Краткий отчёт за сегодня (статус по всем сервисам) |
| `/report today` | Подробный отчёт за сегодня |
| `/report ok` | Только успешные бэкапы за сегодня |
| `/report fail` | Только неуспешные (FAIL/ERROR) за сегодня |
| `/report month` | Сводка за месяц (кол-во OK/FAIL по дням) |
| `/report period YYYY-MM-DD YYYY-MM-DD` | Произвольный период |
| `/services` | Список настроенных сервисов |
| `/check <имя>` | Проверить конкретный сервис прямо сейчас |

### 2.3. Модель отчёта по периоду

Сейчас `BackupReport` содержит только список `ServiceCheckResult` за одну дату. Для отчётов «за месяц» нужно расширить:

```csharp
public class PeriodReport
{
    public DateTime From { get; set; }
    public DateTime To { get; set; }
    public Dictionary<DateTime, BackupReport> DailyReports { get; set; } = new();
    // Агрегаты:
    public int TotalOkDays { get; set; }
    public int TotalFailDays { get; set; }
}
```

Логика проверки периода уже есть в `BackupChecker.CheckBackupForPeriod` — обернём в построитель отчётов.

### 2.4. Форматирование ответов

Telegram `sendMessage` лимит — 4096 символов. Текущий `FormatReport` для большого числа сервисов это превышает. Нужно:
- Разбивать длинный отчёт на несколько сообщений.
- Для `/report` (без аргумента) — короткий формат: только итоги и провалы, без деталей.
- Использовать кнопки (`inline_keyboard`) для быстрых фильтров: `[Сегодня] [Месяц] [Только FAIL]`.

### 2.5. Безопасность

- Каждое входящее сообщение проверяется по `AllowedChatIds`. Если `chat_id` не в списке — молча игнорируем (можно логировать в service.log).
- Если `EnableCommands = false` — бот не вызывает `getUpdates` вообще, работает только рассылка (текущее поведение).
- Токен не логируется в открытую (сейчас исключения могут попасть в логи/MessageBox — добавим маскировку).

### 2.6. UI настроек

В `TelegramSettingsWindow` добавить:
- Чекбокс «Включить приём команд».
- Текстовое поле «Разрешённые Chat ID (каждый с новой строки)».
- Подсказку: первый раз пользователь шлёт `/start` боту, видит свой `chat_id` в ответе службы/логе, добавляет его в список.

### 2.7. Затрагиваемые/новые файлы

|---|---|

## 3. Проверка размера файла бэкапа

**Требование:** для каждого сервиса свой минимальный размер; файл меньше порога → ошибка (подозрение на пустой/битый бэкап). Только минимальный порог, **без максимального** — но порог настраивается **индивидуально для каждого сервиса**.

### 3.1. Новые поля в `Service`

```csharp
public class Service
{
    // ... существующие поля ...

    // Минимальный размер файла в байтах. 0 = проверка отключена.
    // Пример: 5120 = 5 КБ. У каждого сервиса свой порог.
    public long MinFileSizeBytes { get; set; } = 0;

    // Опционально: единица ввода в UI ("5KB", "1MB"), в конфиге хранится в байтах.
    // Пока оставим только байты — проще и однозначнее.
}
```

### 3.2. Изменение логики `BackupChecker`

В `CheckServiceForExpectedDate` (и `CheckBackupForPeriod`) после нахождения файлов за дату — проверить размер каждого подходящего файла:

```
для каждого файла за expectedDate:
    если MinFileSizeBytes > 0 и file.Length < MinFileSizeBytes:
        счётчик "слишком маленьких" файлов++
        пометить файл как не валидный (не засчитывать в foundCount)
        добавить в Details: "Файл <имя>: <размер> < порог"
```

**Правила статуса:**
- Все файлы за дату ≥ порога → `OK` (как сейчас).
- Файлы за дату есть, но все < порога → `FAIL` («Бэкапы есть, но подозрительно маленькие»).
- Часть ≥ порога, часть < → `OK`, но мелкие перечислены в `Details` (предупреждение, не блокирующее).
- `MinFileSizeBytes = 0` → проверка пропускается (обратная совместимость, текущие конфиги не сломаются).

### 3.3. UI

В `ServiceWindow.xaml` и `BulkServiceWindow.xaml`:
- Новое поле «Минимальный размер файла (КБ)» рядом с «Минимум файлов за день».
- Валидация: число ≥ 0; 0 = «не проверять».
- В `MainWindow` в карточке сервиса показывать порог и реальный размер найденного файла (если проверялся).

### 3.4. Тесты

Добавить в `BackupCheckerTests`:
- `FileSize_BelowMin_MarksFail` — файл 1 КБ при пороге 5 КБ → FAIL.
- `FileSize_AboveMin_Ok` — файл 10 КБ при пороге 5 КБ → OK.
- `FileSize_ZeroThreshold_SkipsCheck` — порог 0 → проверка не влияет.

### 3.5. Затрагиваемые/новые файлы

| Файл | Действие |
|---|---|
| `BackupMonitor.Core/Models/Service.cs` | + `MinFileSizeBytes` |
| `BackupMonitor.Core/Services/BackupChecker.cs` | + проверка размера в `CheckServiceForExpectedDate` и `CheckBackupForPeriod` |
| `BackupMonitor.Core/Models/ServiceCheckResult.cs` | опц. + `TotalSizeBytes` для отображения |

## 4. Ревизия Windows-службы

Найденные проблемы при аудите `BackupMonitorService` + `WindowsServiceManager` + `ServiceInstallerHelper`.

### 4.1. 🔴 Критично: `BuildServiceProjectAsync` требует .NET SDK на production

`ServiceInstallerHelper.EnsureServiceExeExistsAsync` при отсутствии `BackupMonitorService.exe` вызывает `dotnet build`. На сервере бэкапов установлен только **runtime**, без SDK → сборка упадёт с «dotnet.exe not found» или ошибкой отсутствия SDK.

**Решение:** доставлять готовый `BackupMonitorService.exe` (self-contained publish) в составе дистрибутива. Опубликовать заранее через `dotnet publish -r win-x64 --self-contained` и класть рядом с GUI. Раздел «публикация» описать в README. Вызов `dotnet build` оставить только как fallback с понятным сообщением «SDK не установлен, используйте предсобранный дистрибутив».

### 4.2. 🟡 `_sentTimesToday` хранится только в памяти

При перезапуске службы в минуту отправки (например, обновление конфига) список `_sentTimesToday` сбрасывается → отчёт уходит дважды.

**Решение:** persist последнего отправленного `timeKey` в файл (`ProgramData/BackupMonitorService/.sentstate.json`) или в `appconfig.json`. При старте читать, при отправке писать.

### 4.3. 🟡 Лог-файл растёт без ограничений

`WriteFileLog` через `File.AppendAllText` → `service.log` через месяц может быть сотни МБ.

**Решение:** простая ротация — при превышении ~5 МБ переименовывать в `service.log.1` (предыдущий `.1` удаляется) и начинать новый. Либо ограничить количество хранимых строк и хранить только последние N.

### 4.4. 🟡 `ReloadConfiguration()` каждую минуту без защиты от частичной записи

Если в момент перечитывания `services.json` его пишет GUI-приложение — можно прочитать наполовину записанный файл → `JsonSerializationException` → список сервисов сбрасывается.

Сейчас в `ConfigurationManager.LoadConfiguration` есть `catch` → `_services = new List()`, то есть **молча теряем все сервисы**. Нужно: при ошибке десериализации сохранять предыдущий успешный список, не затирать пустым.

### 4.5. 🟡 `InstallService` использует `sc.exe create binPath= ...`

Команда правильная, но нет обработки случая «служба с таким именем уже удалена, но SCM ещё не отпустил» (marked for deletion). Нужно: после `sc delete` ждать освобождения имени (poll `IsServiceInstalled` до false с таймаутом), иначе повторная установка упадёт.

### 4.6. 🟢 `WriteFileLog` создаёт директорию — уже исправлено в прошлом проходе.

### 4.7. 🟢 `ShouldSend` с tolerance ±2 мин — корректно для 1-мин таймера.

### 4.8. 🟢 DI-регистрация сервисов как Singleton — правильно, `HttpClient` в `TelegramReportSender` переиспользуется.

### 4.9. Рекомендация: добавить health-check endpoint / heartbeat

Опционально: писать «живой» timestamp в `ProgramData/BackupMonitorService/.heartbeat` каждый цикл. GUI по этому файлу может показать «служба не отзывалась 10 минут» — полезно, если сама служба зависла.

### 4.10. Затрагиваемые/новые файлы

| Файл | Действие |
|---|---|
| `BackupMonitorService/BackupMonitorWorker.cs` | persist sent-state, heartbeat |
| `BackupMonitor.Core/Services/ConfigurationManager.cs` | не затирать сервисы при ошибке чтения |
| `BackupMonitor/Services/ServiceInstallerHelper.cs` | fallback publish вместо build, ожидание удаления службы |

## 5. Дополнительные улучшения

Не из твоего прямого списка, но обнаруженные при аудите — рекомендую включить.

### 5.1. Уведомления об ошибках службы в Windows

Сейчас при ошибке запуска службы пользователь идёт в Event Viewer. Можно ловить `ServiceControllerStatus` переходы и в GUI показывать всплывающее уведомление (балон/тайл).

### 5.2. Кнопка «Проверить сейчас» в карточке сервиса

В контекстном меню `TreeView`-узла — перезапустить проверку только одного сервиса, без полной проверки всех.

### 5.3. Экспорт отчёта

Кнопка «Сохранить отчёт» → текстовый/HTML/CSV файл. Пригодится для отправки почтой или архивирования.

### 5.4. `OnClosed` в MainWindow не диспозит `_scheduler` полностью

`_scheduler?.Stop()` останавливает таймер, но если в этот момент летит `Task.Run(SendScheduledReportAsync)` — он не отменяется. Завернуть в `CancellationTokenSource` и диспозит.

### 5.5. Локализация

Сейчас смесь английского и русского в UI и логах. Вынести строки в `Resources.resx` — упростит перевод и консистентность.

### 5.6. Версионирование конфига

`appconfig.json`/`services.json` без поля `SchemaVersion`. При будущих изменениях модели сложно отличить старый формат от нового. Добавить `"Version": 1` и миграции.

### 5.7. Тесты заблокированы политикой WDAC

На машине разработки `dotnet test` падает с `0x800711C7` (Application Control блокирует свежесобранные DLL). Это не баг кода, но мешает CI. Для CI/релизной машины — настроить исключение пути проекта в политике.

## 6. Порядок внедрения

Рекомендую делать поэтапно, каждое направление — отдельный коммит/PR, чтобы можно было откатить независимо.

| Этап | Что | Зависимости | Объём |
|---|---|---|---|
| **1** | Ревизия службы (раздел 4.1–4.5) | нет | средний |
| **2** | Проверка размера файла (раздел 3) | нет | малый |
| **3** | Интерактивный бот (раздел 2) | этап 2 (для `/check` с размером) | большой |
| **4** | Современный дизайн (раздел 1) | нет, но лучше после 1–3, чтобы верстать финальные поля | большой |
| **5** | Доп. улучшения (раздел 5) | по мере | по желанию |

**Почему такой порядок:**
- Сначала служба — это ядро, и если там баги (SDK, потеря конфига), остальное не имеет смысла.
- Размер файла — маленькое, локальное изменение модели + логики, даёт быстрый видимый результат.
- Бот — самая объёмная фича, опирается на корректную логику проверки.
- Дизайн — финальная отделка; лучше верстать окна один раз под все новые поля (размер, ChatId список), чем переделывать дважды.
